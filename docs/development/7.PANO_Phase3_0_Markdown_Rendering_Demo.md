# PANO Phase 3.0 — Markdown 与数学公式渲染技术验证

## 1. 开发背景与目标

PANO 已完成基础 PDF 阅读、标注及导航功能，后续将进入专业笔记系统开发。目前正式程序及 Phase 0 Demo 中的 `MarkdownRenderer`、`MathRenderer` 均为自研的简化实现。虽然能够显示基础 Markdown 和数学公式，但继续扩展语法的维护成本较高。

本次仅开展独立的技术验证：确认成熟 Markdown 解析库和数学公式渲染库能否在现有 Qt Widgets 技术体系下提供满足专业笔记需求的显示效果，并记录集成成本与实际限制，为后续正式开发提供依据。

本次验证与专业笔记系统的产品设计并行推进，不预先确定笔记树、数据结构、保存机制或正式界面方案。验证完成不代表新引擎已进入正式程序。

### 1.1 范围约束

- 仅在仓库 `demo/` 内开展工作；根目录 `src/`、`resources/`、`xmake.lua`、正式程序数据协议和配置保持不变。
- Phase 0 已有 PDF Demo 作为参考和对照，不修改其原有功能及解析实现，不复刻 PDF 阅读、标注、书库、笔记管理等功能。
- 新 Demo 只需要 Markdown 文本输入、渲染预览、少量验证辅助操作及必要的依赖适配。不实现完整 Markdown 编辑器、所见即所得编辑、语法高亮、自动保存、笔记树或导出。
- 不使用真实书库 `~/Documents/pano`，不读取或修改用户笔记、原始 PDF；本次不需要两份 PDF 测试文件。
- 允许主动编译、运行、截图、视觉检查。避免新增大量测试程序；以一个可操作 Demo 和一份覆盖关键语法的样本为主。

## 2. 现有基础与建议目录

目前 `demo/` 拥有独立 `xmake.lua`，其中已有 `pano-preview-probe`、`pano-math-probe`，以及 `demo/src/note/` 下的旧解析和预览实现。可参考其 `QTextBrowser`、`QTextDocument` 图片资源及公式离屏绘制方式；必要时运行旧探针作为视觉对照，但不需要为本轮重构或扩充它们。

建议新增一个完全独立的小型工程：

```text

├── tools/                       # 原有探针，保持不变
```

建议目标名称 `pano-markdown-demo`。使用 C++20、Qt 6 Widgets、xmake；优先使用已有 Qt SDK。若实际依赖组织需要调整目录，可作小范围修改，但不得将实验性依赖传播到主工程或原 PDF Demo。构建产物、下载缓存、个人路径和临时截图不提交。

## 3. 技术验证方案

### 3.1 Markdown：MD4C

优先采用 [MD4C](https://github.com/mity/md4c)（MIT）作为解析引擎，使用 CommonMark 及所需的 GFM 风格扩展，例如表格、删除线。通过 `MD_FLAG_LATEXMATHSPANS` 识别 `$...$` 和 `$$...$$` 数学片段；注意启用该标志只负责识别公式，并不负责数学排版。

使用公开 API 获取 Markdown 解析事件或 HTML 输出，在解析边界将数学片段交给公式渲染器。根据实际版本核查 `MD_SPAN_LATEXMATH`、`MD_SPAN_LATEXMATH_DISPLAY` 及公式文本事件。尽量利用库自带的语法处理能力，不使用针对全文的简单正则表达式替代 Markdown 解析，也不重新实现完整的 HTML 生成器。

主要验证：标准 Markdown、扩展语法、公式与正文混合、转义及代码块中的美元符号、UTF-8 中文内容、相对路径图片。允许少量与渲染适配有关的代码。

### 3.2 数学公式：JKQTMathText

优先验证 [JKQTMathText](https://jkriege2.github.io/JKQtPlotter/group__jkqtmathtext.html)（JKQtPlotter 的数学排版子库，项目标注 LGPL 2.1 或更高版本）。它可以独立于绘图控件使用，以 Qt 原生方式解析并绘制 LaTeX 数学公式。

- 优先只构建/链接数学排版子库及其必要的公共组件，不引入无关绘图模块。参考上游 CMake 构建说明；即使上游依赖需要用 CMake 编译，Demo 本身仍保持 xmake。
- 优先验证动态链接方式，记录依赖版本、构建选项、链接方式、实际运行所需 Qt 模块及字体资源。避免混用不同 Qt SDK 或不兼容的编译器 ABI。
- 使用上游公式解析、尺寸度量和绘制 API 生成透明背景的公式资源，优先复用 `QTextDocument` 的图片资源机制显示；必要时少量调整行内基线对齐，不自行实现数学公式解析或排版。
- 核查公式渲染失败时的错误反馈；不支持的语法应保留可读原文并标明失败，不得静默丢失公式或用自研渲染器掩盖测试结果。
- 公式资源仅在内存中生成，或存于 Demo 临时输出；不产生正式笔记附件。

JKQTMathText 支持的是 LaTeX 子集，本轮需要验证矩阵、分段函数及多行对齐等实际表现，而不能根据上游文档直接判定已经满足要求。对于字体、库及其传递依赖，应记录实际许可证与分发义务；暂不制作正式安装包。

### 3.3 Qt 预览与替代路线

第一轮完整路线：

```text
Markdown UTF-8 源文
      ↓
MD4C 解析（正文结构、数学片段）
      ├── 普通 Markdown → Qt 可显示的富文本
      └── 数学片段 → JKQTMathText → 公式图像资源
      ↓
QTextDocument / QTextBrowser
      ↓
预览窗口
```

重点观察行内公式基线、独立公式排版、图片尺寸及表格布局是否受 Qt 富文本能力限制。注意避免 HTML 注入和隐式加载外部资源；测试仅支持本地样本目录内图片，不自动打开外部链接，不进行网络请求。公式与图片资源应使用独立标识，避免与原文冲突。

Qt 原生 `QTextDocument::setMarkdown()` 可作为普通 Markdown 的轻量对照，但不需要建立第二套完整实现。若原生组合在重要公式或排版上存在明显限制，记录具体失败样例和原因；将 KaTeX + Qt WebEngine（或其他成熟引擎）列为后续候选。当前仓库 `AGENTS.md` 明确不引入 WebEngine 或网络依赖，本轮不实施该替代路线，也不修改仓库约定。

## 4. 最小验证界面

使用普通 Qt Widgets 窗口即可，不进行产品化界面设计。

```text

│ PANO Markdown Demo                                           │

├───────────────────────────┬──────────────────────────────────┤
│ Markdown 源码             │ 渲染预览                         │
│                           │                                  │
│ # 结构动力学              │ 结构动力学                       │
│                           │                                  │
│ $$                        │       公式显示区域               │
│ m\ddot u + ku = 0         │                                  │

├───────────────────────────┴──────────────────────────────────┤
│ 渲染耗时 / 公式数量 / 失败数量（有失败时提供具体信息）         │
└──────────────────────────────────────────────────────────────┘
```

左侧使用 `QPlainTextEdit` 输入，右侧使用 `QTextBrowser` 或等效 Qt 原生预览控件，以 `QSplitter` 支持改变预览宽度。启动时加载综合样本，也允许直接修改文本。手动重新渲染即可；如果实现简单，可增加约 300 ms 的延迟自动预览，但不需要实时逐字符排版。字号、浅深色可以用简易控件切换，只为验证渲染效果，不接入正式主题系统。不实现文件写回和编辑状态持久化。

状态栏可记录 Markdown 解析、公式绘制及整体预览更新耗时，区分首次渲染和重复渲染，不设置未经实测的强制性能指标。

| 编号 | 验证内容 | 主要观察项 |
| --- | --- | --- |
| V01 | 依赖与构建 | Qt 6 + xmake 环境可重复构建；记录具体版本与运行依赖 |
| V02 | 基础 Markdown | 标题、嵌套列表、引用、表格、代码、链接、中英文显示 |
| V03 | 数学识别 | 行内/独立公式、跨行数学、代码块与转义边界 |
| V04 | 基础数学排版 | 分式、根号、上下标、希腊字母、积分、求和、粗体向量 |
| V05 | 专业数学排版 | 矩阵、分段函数、多行对齐、括号尺寸、复杂公式 |

验收主要采用综合样本的真实窗口和截图目视检查。行内公式不能明显漂移或无故造成大行距；独立公式不能丢失或严重模糊；矩阵等结构需要检查数学含义是否正确，而非仅判断生成了非空图像。对宽度不足的长公式，可使用水平滚动或清晰的溢出处理，不强制缩小至不可读。

不要求全部项目通过才允许结束 Demo。V05、V06 和 V07 中的关键失败本身就是技术验证成果，需要明确判断是否阻碍正式应用。Windows 若暂不可用，应标记未验证并给出构建步骤，不将 Linux 结果视为 Windows 通过。

## 7. 实施顺序与交付

1. 独立构建：确认 MD4C、JKQTMathText 依赖可用，完成最小窗口。
2. 分别验证：先测试普通 Markdown，再独立测试公式渲染，区分两个层次的失败。
3. 混合预览：接入综合样本，检查公式、图片、表格和正文混排。
4. 真实运行：改变窗口宽度、字号、主题，编辑几种公式并重新渲染；按可用平台验证构建。
5. 记录结论：更新 `demo/markdown/README.md` 和 `results.md`，保留少量有代表性的截图（建议本地 `build/probe/`，只在有必要时提交精选结果）。

`results.md` 至少说明：实际依赖与版本；构建和运行命令；每项验证的通过/部分通过/失败/未验证状态；关键公式支持情况；典型截图；已测耗时及平台；已知问题、可行的低成本解决方案与推荐技术路线。

最终结论应区分三种情况：

- **可采用**：原生组合能够满足关键 Markdown 和专业公式显示需求，集成成本可控。
- **有条件采用**：存在少量明确的适配问题，可在正式开发中以较小代价解决。
- **暂不采用**：重要公式、行内排版或部署存在实质障碍，建议再评估其他成熟方案，不继续扩大自研解析器。

本轮到此结束。不得直接将 Demo 代码合入正式程序，也不提前开发正式笔记界面。专业笔记系统的数据、交互和界面方案由后续独立讨论确定。
